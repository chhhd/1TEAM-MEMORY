# CVE 조사 절차

## 1. 버전 정보 정리

- recon 핸드오프에서 소프트웨어명 + 버전을 표로 정리 (예: `nginx 1.18.0`, `WordPress 6.2`, `log4j 2.14.1`)
- 버전을 알 수 없는 경우, 에러 페이지/디버그 모드/변경 로그 노출 여부로 추정 시도

## 2. CVE 검색

- NVD(nvd.nist.gov), 벤더 보안 공지, GitHub Security Advisories 등에서 버전대에 해당하는 CVE 조회
- CVSS 점수, 공격 벡터(네트워크/인증 필요 여부), 공개 PoC 유무 확인
- 여러 CVE가 나오면 CVSS 높은 순 + 공개 PoC 있는 것 우선 정리

## 3. 적용 가능성 검증 (비파괴적 우선)

- 배너/응답 헤더의 상세 버전과 CVE 대상 버전 범위 재대조
- 가능하면 트리거하지 않고 확인 가능한 방법 우선 사용 (특정 엔드포인트 존재 여부, 설정 파일 노출 등)
- 실제 트리거가 필요한 경우, 대상 상태를 변경하지 않는 최소한의 PoC만 사용하고 사전에 팀과 공유

## 4. 판정 기준

- `suspected`: 버전 대조상 취약할 가능성 있음, 실제 동작 미확인
- `confirmed`: 비파괴적 방법으로 실제 취약 동작 확인
- 패치 백포트로 버전만으로 판단 불가한 경우 반드시 `suspected`로 유지하고 비고에 명시

## 5. 기록

cve-agent 정의의 "기록" 섹션 형식을 따른다. 참고한 CVE 링크/공지를 raw 파일에 남긴다.

## 금지 사항

- DoS성 CVE를 실제로 트리거하지 않는다
- 공개 익스플로잇 코드를 검토 없이 실행하지 않는다 (원격 대상에 임의 페이로드를 그대로 던지지 않기)
- 데이터 파괴/변조를 유발하는 검증 방법 대신 항상 비파괴적 대안을 먼저 시도
