# Access Control (IDOR/Auth) 체크리스트

## 0. 준비

- 서로 다른 권한의 테스트 계정 확보 (최소 일반 사용자 2개, 가능하면 관리자 1개)
- 각 계정의 세션 토큰/쿠키를 구분해서 보관 (실수로 섞어 쓰지 않도록 이름 붙이기)

## 1. 수평 권한 상승 (IDOR)

- [ ] 계정 A로 리소스 생성 (주문, 게시글, 프로필 등) → 응답에서 리소스 ID 확보
- [ ] 계정 B 세션으로 해당 ID를 직접 요청 (GET) — 조회 가능한가?
- [ ] 계정 B 세션으로 해당 ID를 수정(PUT/PATCH) — 가능한가?
- [ ] 계정 B 세션으로 해당 ID를 삭제(DELETE) — 가능한가? (실제 삭제는 신중히, 테스트 데이터로만)
- [ ] ID가 숫자/순차적이면 인접 ID를 순회했을 때 타 계정 데이터가 나오는지 (1~2건만 확인, 대량 수집 금지)
- [ ] ID가 UUID/난수라도, 다른 응답(목록 API 등)에서 타인의 ID가 노출되는 경로가 있는지 확인

## 2. 수직 권한 상승

- [ ] 관리자 전용 페이지의 API를 일반 계정 토큰으로 직접 호출 (프론트 라우팅 우회)
- [ ] 미인증 상태(토큰 없이)로 같은 API 호출 — 응답 코드/바디 확인
- [ ] 역할(role) 파라미터가 요청 바디/헤더에 있다면 클라이언트에서 값을 변조해 전송 (예: `role: admin`)

## 3. 인증/세션

- [ ] 로그아웃 후 이전 토큰이 여전히 유효한지 (세션 무효화 확인)
- [ ] 비밀번호 재설정 토큰이 예측 가능하거나 만료/1회성이 지켜지지 않는지
- [ ] JWT 사용 시: `alg: none`, 서명 검증 누락, 만료(`exp`) 미확인 여부
- [ ] 초대 링크/공유 링크에 만료·권한 스코프가 있는지

## 4. 판정 기준

- `suspected`: 다른 계정 데이터가 응답에 일부 노출되었으나 재현 1회뿐이거나 우연 가능성 있음
- `confirmed`: 동일한 요청을 재현했을 때 일관되게 타 계정 데이터 접근/변경 가능
- severity: 열람만 가능=medium, 수정/삭제 가능=high, 관리자 권한 탈취=critical

## 5. 기록

access-control-agent 정의의 "기록" 섹션 형식을 따른다. 두 계정의 요청/응답을 나란히 남겨야
재현 가능한 근거가 된다.

## 금지 사항

- 실제 타인(다른 참가자/실사용자) 데이터로 보이는 것을 발견하면 대량 조회 없이 즉시 중단, 팀 보고
- 세션 하이재킹 취약점을 발견해도 실사용자 세션을 실제로 가로채 행동하지 않는다
- 삭제/변경 PoC는 반드시 자신이 만든 테스트 리소스에 대해서만 수행
